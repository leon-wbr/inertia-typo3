# TYPO3 Inertia adapter: feature parity with Inertia v3

Audited against `inertiajs/inertia-laravel` 3.7.0 and `@inertiajs/core` 3.11.0, the latest releases on 2026-11-03. The adapter was audited at `d7a8f3b` (main, after #11).

This list says what the adapter still lacks to be a complete Inertia v3 server adapter. [`Build/Parity/parity.json`](Build/Parity/parity.json) records the same versions and the protocol surface. A weekly check reports when Inertia releases something newer: see [Keeping this list in sync](#keeping-this-list-in-sync).

How to read the tables:

- **Defined in**: the Inertia docs page and/or the source of the reference implementation. `inertia-laravel` links are pinned to [v3.7.0](https://github.com/inertiajs/inertia-laravel/tree/v3.7.0), client links to [@inertiajs/core v3.11.0](https://github.com/inertiajs/inertia/tree/v3.11.0/packages/core).
- **Status**:
  - `supported` means the adapter implements it and a test exercises it.
  - `partial` says what is missing. `partial (untested)` means code exists but no test covers it.
  - `missing` cites where upstream defines the feature.
  - `n/a` says why the feature doesn't apply to TYPO3.
- **Adapter coverage**: the adapter code and the tests that cover it. Unit tests are in `Tests/Unit`, functional tests in `Tests/Functional`, and Playwright e2e tests in `example/e2e`.
- **Priority**:
  - P1: needed for a complete v3 adapter, or commonly used.
  - P2: useful.
  - P3: niche.

Overview: 76 supported, 14 partial (5 of them untested), 40 missing, 15 not applicable.

## Next up

1. **Rescued deferred props.** Add `defer(..., rescue: true)`, `rescuedProps` and logging. With SSR, this is what the community adapters page means by "partial".
2. **Server-side rendering.**
   - An HTTP gateway to the Inertia SSR server (`POST /render`) that falls back to client-side rendering on failure.
   - The SSR `head` goes into TYPO3's `PageRenderer`, and the SSR `body` replaces the page script in `App.html`.
   - SSR can be turned off per request or path.
   - In development, Vite's `/__inertia_ssr` endpoint does the rendering.
   - Bundle detection, a health check, console commands and site settings.

   This is its own pull request, and closes group 6.
3. **Session-backed `clearHistory()` and `preserveFragment()`.** Both must survive a redirect, as in a logout. This is bug 4.
4. **Error pages through Inertia.** Hook into TYPO3's site `errorHandling`, so that a 404 or 500 on an Inertia visit renders a component with the shared props instead of HTML, which the client shows in its error modal.
5. **File uploads with PUT/PATCH.** Honour `_method` on multipart POSTs, as the Inertia docs advise, or parse multipart bodies with `request_parse_body()` on PHP 8.4. This is bug 5.
6. **History encryption settings.** Add a global switch (site or extension setting) and an `EncryptHistory` middleware.
7. **Testing helpers.**
   - Add `reload()`, `reloadOnly()`, `reloadExcept()`, `loadDeferredProps()` and flash assertions on redirects.
   - Add tests for every `partial (untested)` row.
8. **DX parity.**
   - A per-response root view and view data, a URL resolver, a global component transform and `back()`.
   - `ProvidesInertiaProperties` and `ProvidesInertiaProperty`, and the array form of `append()`/`prepend()`.
   - A switch for `sharedProps`.
9. **Big integers.** Add `preserveBigIntegers` and the `$bigint` markers.
10. **Precognition.** A `Precognition` request short-circuits to 204 or 422 through a validation hook.
11. **Live props and DevTools.** These need a broadcaster and a request recorder, so they come last.

## Getting listed on Inertia's community adapters page

The [community adapters page](https://inertiajs.com/docs/v3/installation/community-adapters#listing-your-adapter) lists adapters through a pull request to [inertiajs/docs](https://github.com/inertiajs/docs). These are its requirements and where the adapter stands on each:

- [x] It implements the [protocol](https://inertiajs.com/docs/v3/core-concepts/the-protocol) for a supported Inertia version: v3, see group 1 below.
- [x] It documents its installation, root template and shared data APIs: [README](README.md#installation-in-your-own-project), sections "Installation in your own project" (with the `App.html` root view) and "Shared props".
- [x] It states which Inertia version and protocol features it supports: the README's [Requirements](README.md#requirements) and [Compared with inertia-laravel](README.md#compared-with-inertia-laravel), and this file.
- [ ] It has an active maintainer and a release on its language's package registry. `leon-wbr/inertia` isn't on Packagist yet, and the repository has no tags or releases.

## Known bugs (found in the audit of #11)

1. **Fixed** (conformance C37, C39, C32). QUERY redirects are not converted to 303. [`InertiaMiddleware.php:88`](Classes/Middleware/InertiaMiddleware.php#L88) lists only `PUT`, `PATCH`, `DELETE`. Repro: an Inertia `QUERY /contact` whose handler returns `new RedirectResponse('/x', 302)` comes back as 302, so the browser repeats QUERY instead of GET (protocol and inertia-laravel 3.6.0 say 303).
2. **Fixed** (conformance C37, C39, C32). `Vary: X-Inertia` is lost on responses the middleware replaces. [`InertiaMiddleware.php:78`](Classes/Middleware/InertiaMiddleware.php#L78) adds `Vary` before [`:84-94`](Classes/Middleware/InertiaMiddleware.php#L84) swap in new `RedirectResponse`/`Response` objects. Repro: an Inertia POST whose handler returns a 302 to `/page#x` gets a 409 without `Vary`; an Inertia POST with an empty 200 gets a 303 without `Vary`.
3. **Fixed** (conformance C37, C39, C32). Prefetch requests get fragment redirects as 409 `X-Inertia-Redirect`. [`InertiaMiddleware.php:92`](Classes/Middleware/InertiaMiddleware.php#L92) never checks `Purpose: prefetch`. Repro: `GET /a` with `X-Inertia: true` and `Purpose: prefetch`, handler 302 to `/b#c`: the response is a 409. The protocol (the-protocol.mdx line 705) and inertia-laravel (`test_redirect_with_hash_fragment_is_not_intercepted_for_prefetch_requests`) pass the redirect through unchanged.
4. `clearHistory()` before a redirect is silently dropped. The flag lives on the per-request service ([`InertiaService.php:137-140`](Classes/Service/InertiaService.php#L137), read at [`:322`](Classes/Service/InertiaService.php#L322)), not in the session as in inertia-laravel. Repro: a logout handler calls `$inertia->clearHistory()` and returns `$inertia->redirect('/')`; the page object of the follow-up GET has no `clearHistory: true` (cf. `HistoryTest::test_the_history_can_be_cleared_when_redirecting`).
5. Multipart PUT/PATCH (file uploads) arrive empty or garbled, and `_method` spoofing is not supported. [`InertiaMiddleware.php:204-207`](Classes/Middleware/InertiaMiddleware.php#L204) only repairs JSON bodies. Repro: `router.put('/profile', {avatar: file})` sends `multipart/form-data`; the handler sees `parse_str()` output of the raw body and no uploaded file. POSTing with `_method: 'put'`, as the docs advise, is treated as a POST.

## Keeping this list in sync

[`Build/Scripts/parity.mjs`](Build/Scripts/parity.mjs) runs two checks against [`Build/Parity/parity.json`](Build/Parity/parity.json), which records the audited versions and every header and page-object field the client uses. Each header and field has a status.

- **`local`** is offline and runs in `ddev verify`, so it runs in CI and in Dependabot's pull requests.
  - It reads the `@inertiajs/core` installed in `example/`, which `@inertiajs/react` pulls in.
  - It extracts the header names from `dist/index.js`, and the keys of `Page`, `ScrollProp` and `LiveProp` from `types/types.d.ts`.
  - It fails when the client uses a name that `parity.json` doesn't list.
  - It also fails when this file's "Audited against" line names different versions than `parity.json`.
  - [Dependabot](.github/dependabot.yml) bumps `@inertiajs/*` weekly, so a new client feature with a new header or field shows up as a failing pull request.
- **`upstream`** needs the network and runs weekly in [`.github/workflows/parity.yml`](.github/workflows/parity.yml).
  - It compares the audited versions with the latest `inertiajs/inertia-laravel` on Packagist and `@inertiajs/core` on npm.
  - It diffs the latest releases' surfaces against `parity.json`:
    - the client's headers and page fields, from the npm tarball;
    - inertia-laravel's `Header` constants, `ResponseFactory` methods and `src/` files, from GitHub.
  - On any difference, it opens or updates one issue labelled `inertia-parity`. The issue links the release notes in between.

Run them locally:

```sh
ddev parity                  # local; or: node Build/Scripts/parity.mjs local
ddev parity upstream         # latest releases
node --test Build/Scripts/   # the checks' own tests, which fake drift
```

When a check fires:

1. Read the linked compare views and releases. inertia-laravel's `CHANGELOG.md` lags its releases, so use the GitHub releases and commits.
2. Update the tables above for every new or changed feature, with its source and a priority.
3. For a new client header or page field, add it to `parity.json` under `client` with its status.
4. Run `node Build/Scripts/parity.mjs record`. It stores the latest versions and inertia-laravel's surface in `parity.json`.
5. Update the "Audited against" line at the top of this file to match, then run `ddev parity` and `ddev parity upstream`. Both should say "In sync".
6. Close the tracking issue with the pull request.
